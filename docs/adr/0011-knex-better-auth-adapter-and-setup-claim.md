# Verify the Knex-backed Better Auth adapter and one-time setup claim

Better Auth 1.7.23 ships no Knex adapter, so identity tables are read and
written through the documented custom-adapter interface (`createAdapterFactory`
from `better-auth/adapters`) over the shared Knex pool
(`apps/web/lib/auth/knex-adapter.ts`). This confirms the requirement in
ADR 0010 rather than assuming native Knex support.

## Schema authority

Knex migrations remain the only schema authority. The `identity_and_workspaces`
migration declares `user`, `session`, `account`, `verification`, `workspaces`,
`workspace_memberships` and the singleton `installation` row; Better Auth's own
migration tooling is never run. The adapter translates between the camelCase
field names the library uses and the snake_case columns the migration owns, and
`apps/web/test/knex-auth-adapter.test.ts` fails if the pinned library expects a
column the migration does not declare. Identity ids are UUIDs generated by the
library, so the text id columns accept them without a database default.

## Atomicity

- Every credential and session write runs inside the caller's transaction
  (`transaction` config), so a failed sign-up leaves no half-created user.
- `consumeOne` is a single `DELETE ... RETURNING`, so a one-time token is
  consumed by exactly one concurrent caller; `incrementOne` applies guarded
  counters in one `UPDATE`. Both are verified under concurrent callers.
- The setup claim is gated by one conditional
  `UPDATE installation SET setup_completed_at = ... WHERE setup_completed_at IS NULL`
  before any identity is created. A replay, or a second concurrent claim, loses
  that update and returns `setup-already-complete` without creating an
  administrator, workspace or membership; a provisioning failure restores the
  claim.

## Setup token and admission

The one-time token is installation-held: it comes from `SETUP_TOKEN` in the
environment, is compared in constant time, is never stored, and only its hash is
recorded once spent. Setup therefore needs no SMTP delivery and does not assert
email ownership: the first administrator's `emailVerified` stays `false` and no
verification email is sent.

Core owns admission: `auth.admission` resolves the caller's workspace from
`workspace_memberships` and refuses a principal naming any other workspace, and
installation administration is limited to the user recorded by the setup claim.
HTTP routes and server actions build the principal from the stored session
only, never from request input, and direct core calls receive the same checks.

## Sign-up surface

Public registration stays closed. Better Auth's `disableSignUp` also blocks the
library's `signUpEmail` endpoint for server-side callers, which the setup claim
needs, so the library's own `/api/auth/sign-up/email` route is refused at the
HTTP boundary instead and core reports `registration-closed` for any sign-up
attempt. Invitation acceptance in a later ticket reuses the same server-side
provisioning path.
